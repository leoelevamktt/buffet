# Admin MFA Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Require authenticator MFA for every panel account, with administrator-authorized enrollment and usable recovery.

**Architecture:** Password validation issues only a short-lived HttpOnly preauthentication cookie. A PostgreSQL transaction verifies the enrollment authorization or existing factor and issues a version-bound full session. A separate, trusted maintenance operation authorizes the first protected administrator.

**Tech Stack:** Existing React/TypeScript, Node 24, PostgreSQL; OTPAuth 9.5.2, qrcode 1.5.4, Node crypto AES-256-GCM.

**Spec:** `docs/superpowers/specs/2026-10-28-admin-mfa-design.md` (user chose mandatory MFA for everyone plus individual invitation).

## Global Constraints

- All private panel accounts require MFA; public customer signing and quotes remain usable.
- Password alone cannot obtain a full session or enrollment QR Code.
- Invitation: one account, single use, 30 minutes; replacing it invalidates pending enrollment.
- Preauthentication: 5 minutes, maximum 5 second-factor failures, plus persistent per-account throttling.
- TOTP: SHA1, 6 digits, 30 seconds, window 1; accepted counters cannot be reused.
- Eight random 96-bit recovery codes; only hashes stored; recovery forces new verified enrollment.
- TOTP secrets encrypted with independent `MFA_ENCRYPTION_KEY`; no secrets/codes in logs or user listings.
- User/account locks precede challenge/invitation locks; commits preserve failed-attempt counters.
- Existing business data and signed documents must remain intact.
- Execute inline in this chat and request an independent whole-change review before publication.

## Review Focus

- A replaced invitation must invalidate a QR Code already displayed (Task 2).
- Two concurrently accepted codes must not produce duplicate sessions or consume one backup twice (Task 2).
- Password resets and account deactivation during preauthentication must prevent completion (Task 2).
- Browser refresh during recovery must resume safely without storing plaintext codes (Task 3).
- Missing/corrupt encryption key must fail closed, while rollback must not revive pre-MFA sessions (Tasks 2 and 4).

## Files and responsibilities

- `api/_mfa-crypto.js`: secret generation/encryption, TOTP validation, QR rendering, recovery and invitation hashing.
- `api/_mfa.js`: preauthentication cookie, transactional enrollment, invitation authorization, recovery, code regeneration.
- `api/mfa.js`: request validation and MFA endpoint dispatch.
- `api/session.js`, `api/_session.js`: password-only stage and server-side MFA session enforcement.
- `api/users.js`, `src/auth.ts`: safe MFA enrollment status for user management.
- `scripts/neon-schema.sql`: additive MFA fields/tables; maintenance grants and bootstrap outside source-controlled secrets.
- `src/components/MfaAccess.tsx`, `MfaRecoveryCodes.tsx`: login/enrollment/recovery and single-display backup UI.
- `WorkspaceGate.tsx`, `ProfileView.tsx`, `UsersView.tsx`, `src/styles.css`: integrate with existing access/account/user screens.
- `scripts/mfa-crypto.test.mjs`, `mfa-db.test.mjs`, existing security/auth tests and CI: regression coverage.
